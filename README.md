Бай: зөвхөн `http://localhost:3000` ([server.js](server.js), Express). Ачаалал: 20 VU, VU бүр нэг давталтад `/cart/add`, `/report`, `/pay`-г нэг нэгээр дуудаад 1с хүлээнэ.

## 1. Чанарын сценариуд (6 хэсэгтэй формат)

### Performance: `/cart/add`

| Хэсэг | Агуулга |
|---|---|
| Тойм | Хэвийн ачааллын үед хэрэглэгч бараа сагсанд нэмэхэд хариу хурдан ирэх |
| Системийн төлөв | API хэвийн ажиллаж байна. `/report`, `/pay` нь зэрэг ачаалалтай |
| Орчны төлөв | localhost, Node.js нэг процесс, хэвийн ачаалал: **20 VU**, ≈15 хүсэлт/с `/cart/add` руу, 1 минут |
| Гадаад өдөөлт | Хэрэглэгч "Сагсанд нэмэх" дарна → `POST /cart/add` |
| Шаардлагатай хариу | `200 OK`, `{ ok: true }` |
| Хэмжүүр | 1 минутын цонхонд хүсэлтийн **95% нь 20ms-ээс**, **99% нь 50ms-ээс** хурдан |

### Reliability: `/pay`

| Хэсэг | Агуулга |
|---|---|
| Тойм | Хэвийн хэрэглэгчийн төлбөрийн үйлдэл найдвартай амжилттай болох |
| Системийн төлөв | API хэвийн ажиллаж байна. Төлбөрийн gateway хааяа timeout өгдөг (~5%) |
| Орчны төлөв | localhost, **20 VU**, ≈15 хүсэлт/с `/pay` руу, 1 минут |
| Гадаад өдөөлт | Хэрэглэгч "Төлөх" дарна → `POST /pay` |
| Шаардлагатай хариу | `200 OK`, `{ paid: true }`. Алдаа гарвал `500` ба тайлбартай JSON |
| Хэмжүүр | **POFOD** (нэг хүсэлт амжилтгүй болох магадлал) = error rate **< 8%** (1 минутын цонх) |

### Availability: сервер унах ба сэргэх

| Хэсэг | Агуулга |
|---|---|
| Тойм | Сервер гэнэт зогсоод дахин асахад үйлчилгээ хэр хурдан сэргэх, нийт хэр хүртээмжтэй байх |
| Системийн төлөв | API хэвийн ажиллаж, 20 VU ачаалалтай байна |
| Орчны төлөв | localhost, 2 минутын тест. Сервер дунд нь **10 секунд** зогсоно |
| Гадаад өдөөлт | **Эвдрэл (crash):** серверийн процесс гэнэт зогсоно (Ctrl+C / kill) |
| Шаардлагатай хариу | Зогсолтын үед хүсэлтүүд шууд алдаа (connection refused) буцаана, гацахгүй. Сервер дахин асмагц хүсэлтүүд хэвийн `200` болно |
| Хэмжүүр | 2 минутын цонхонд амжилттай хүсэлтийн хувь (availability) **≥ 90%**. Дахин асаасны дараа сэргэх хугацаа **≤ 15с** |

### Нэмэлт (4 дэх) сценарио: `/report` performance

| Хэсэг | Агуулга |
|---|---|
| Тойм | Хүнд тайлан хэвийн ачаалалд хүлээгдэх хугацаандаа гарах |
| Системийн төлөв / орчин | Хэвийн, localhost, 20 VU, 1 минут |
| Гадаад өдөөлт | `GET /report` |
| Шаардлагатай хариу | `200 OK`, `{ rows: 20000 }` |
| Хэмжүүр | Хүсэлтийн **95% нь 450ms-ээс** хурдан |

**Сайн сценариогийн 5 шинжээр шалгахад:**
- **Итгэмжтэй:** тоонууд хэмжилтэд суурилсан.
- **Үнэ цэнэтэй:** хэрэглэгчийн бодит үйлдлүүд (сагс, төлбөр).
- **Тодорхой:** endpoint, ачаалал, цонхыг нэрлэсэн.
- **Нарийн:** p95/p99 болон хувиар илэрхийлсэн.
- **Ойлгомжтой:** нэг сценарио нэг хэмжүүрт төвлөрсөн.

## 2. SLO

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл | k6 threshold ([slo-test.js](slo-test.js)) |
|---|---|---|---|---|
| Performance | `/cart/add` latency | **p95 < 20ms**, **p99 < 50ms** | 20 VU тогтмол, 1 мин | `http_req_duration{name:cart}: ['p(95)<20', 'p(99)<50']` |
| Reliability | `/pay` error rate | **< 8%** | 20 VU, 1 мин | `http_req_failed{name:pay}: ['rate<0.08']` |
| Availability | бүх хүсэлтийн амжилтын хувь (checks) | **≥ 90%** (k6-д `> 0.90`) | 20 VU, 2 мин, 10с зогсолт | `checks: ['rate>0.90']` |
| Нэмэлт | `/report` latency | **p95 < 450ms** | 20 VU, 1 мин | `http_req_duration{name:report}: ['p(95)<450']` |

**Босго сонгосон үндэслэл:**
- **Performance:** [pass.txt](results/pass.txt)-д `/cart/add` p95 = 1.31ms, p99 = 5.4ms гарсан. Зааврын 200ms нь юу ч хэмжихгүй сул босго болно. Тиймээс ~15 дахин нөөцтэй 20ms-ийг сонгосон: регресс (жишээ нь DB дуудлага нэмэгдэх) гарвал барьж чадна.
- **Reliability:** серверт 5% алдаа суулгасан. 1 минутад ~930 `/pay` хүсэлт байхад (pass.txt: 49 / 930) санамсаргүй хэлбэлзэл ±0.7% орчим байдаг тул 8% бол бодитой, гэхдээ алдаа 2 дахин өсвөл барих босго.
- **Availability:** 2 минутад 10с зогсолт ≈ 8.3% цаг. 90% нь энэ туршилтыг "ирмэг дээр" шалгах босго.
- **Нэмэлт:** `/report` хамгийн ихдээ 400ms хүлээдэг. Үүн дээр 50ms нөөц нэмсэн.

**Error budget (цагаар):** 2 мин × (1 − 0.90) = 120с × 0.10 = **12 секундийн "эвдрэх эрх"**.

## 3. PASS — `k6 run slo-test.js` → [results/pass.txt](results/pass.txt)

| Threshold | Үр дүн |
|---|---|
| `http_req_duration{name:cart}` p(95)<20 / p(99)<50 | ✓ p(95)=1.31ms / ✓ p(99)=5.4ms |
| `http_req_failed{name:pay}` rate<0.08 | ✓ rate=5.26% (49 / 930) |
| `checks` rate>0.90 | ✓ rate=98.24% (2741 / 2790) |
| `http_req_duration{name:report}` p(95)<450 | ✓ p(95)=391ms |

Нийт 2790 хүсэлт (45.65/s), **exit=0**.

## 4. Мини chaos — `k6 run -e DURATION=2m slo-test.js` → [results/chaos.txt](results/chaos.txt)

`duration`-ыг `-e DURATION=2m`-ээр 2 минут болгосон. Тест эхэлснээс 40 секундын дараа серверийг SIGINT-ээр (Ctrl+C-тэй адил) зогсоож, 10 секунд хүлээгээд `node server.js`-ээр дахин асаасан ([results/chaos-timeline.txt](results/chaos-timeline.txt)):

```
20:35:53 server зогсоов (SIGINT = Ctrl+C)
20:36:04 server дахин асаав (node server.js)
```

| Threshold | Үр дүн |
|---|---|
| `checks` rate>0.90 (**Availability**) | ✗ rate=**88.03%** (4997 / 5676) → **FAIL** |
| `http_req_failed{name:pay}` rate<0.08 (**Reliability**) | ✗ rate=**14.42%** (273 / 1892) → **FAIL** |
| `http_req_duration{name:cart}` p(95)<20 / p(99)<50 | ✓ 1.31ms / ✓ 2.71ms |
| `http_req_duration{name:report}` p(95)<450 | ✓ 389.12ms |

Нийт 5676 хүсэлт, `http_req_failed` = 11.96% (679 / 5676), **exit=99**.

**`connection refused` алдааг секундээр тоолоход** (`chaos.txt`-ийн лог мөрүүдээс):
- 20:35:53-аас 20:36:04 хүртэл нийт **610** алдаа.
- Бүтэн секунд бүрд **55–60** алдаа гарсан.
- Сервер асмагц, 20:36:04 секунд дотор алдаа зогссон. Өөрөөр хэлбэл дахин асаасны дараах сэргэх хугацаа **< 1с**. Нийт зогсолт ≈ 11с (`node` асах хугацаа орсон).

**Бодит availability (хүсэлтээр):** 4997 / 5676 = **88.03%** < 90% → SLO зөрчигдсөн.

**Error budget-ийг хоёр аргаар тооцоход:**
- **Цагаар:** 120с × 10% = 12с budget. Бодит зогсолт ≈ 11с (9.2%) тул **budget-д багтсан**.
- **Хүсэлтээр:** 5676 × 10% ≈ **567** алдаа зөвшөөрөгдөнө. Бодитоор **679** алдаа гарсан (610 нь зогсолтоос, 69 нь `/pay`-ийн хэвийн 5% алдаа) тул **112-оор хэтэрсэн**.

**Хоёр тоо яагаад зөрж байна вэ?** k6-ийн `checks` нь цагийн биш, **хүсэлтийн** хувь. Хэвийн үед нэг давталт ≈ 1.3с үргэлжилдэг (`/report` 200–400ms + `sleep(1)`). Тиймээс 20 VU секундэд ~46.8 хүсэлт явуулдаг. Сервер унасан үед бүх хүсэлт шууд `connection refused` буцааж, `/report`-ын хүлээлт алга болдог. Үүний улмаас давталт ≈ 1.0с болж, секундэд **60** хүсэлт явсан. Ингэснээр зогсолтын нэг секунд хэвийн секундээс ~28% илүү хүсэлт "идэж", цагаар 9.2% байсан зогсолт хүсэлтээр 10.7% (610/5676) болсон. Үүн дээр `/pay`-ийн хэвийн алдаа нэмэгдэж, budget хэтэрсэн.

**Reliability яагаад зэрэг FAIL болсон бэ?** Сервер унасан үед `/pay`-ийн хүсэлт бүр унадаг тул нэг эвдрэл availability болон reliability хоёр SLO-г зэрэг зөрчсөн (5% → 14.42%). Хоёр SLI-г тусгаарлахын тулд reliability-д зөвхөн сервер **хариу өгсөн** хүсэлтүүдийг тоолох хэрэгтэй (жишээ нь `status === 500`-г л алдаа гэж тоолох, `status 0`-ийг (холболт тасарсан) availability-д тооцох).

**Дүгнэлт:** 10 секундын зогсолтод 90% нь хэт өөдрөг SLO биш. Цагаар budget-д багтсан ч хүсэлтээр тооцоход зогсолтын үеийн "хурдан алдаа" болон суурь 5% алдаа нийлж хэтэрсэн. Хоёр сонголт байна: (a) availability SLI-г `/pay`-ийн суулгасан алдаанаас салгах, (b) зогсолтыг богиносгох (автоматаар дахин асаах, жишээ нь systemd/pm2).

## 5. Зориуд FAIL — `k6 run slo-test-fail.js` → [results/fail.txt](results/fail.txt)

[slo-test-fail.js](slo-test-fail.js)-д `/report`-ын threshold-ыг `p(95)<100` болгосон.

```
    http_req_duration{name:report}
    ✗ 'p(95)<100' p(95)=391.73ms
...
level=error msg="thresholds on metrics 'http_req_duration{name:report}' have been crossed"
exit=99
```

- FAIL-ийг `✗ 'p(95)<100' p(95)=391.73ms` мөр харуулж байна. Бусад threshold бүгд ✓.
- k6 **exit code 99** буцаасан (`echo "exit=$?"`). PASS үед exit 0 байсан. CI pipeline энэ 0 биш кодоор build-ийг зогсоодог.
- `/cart/add`-ыг `p(95)<50` болговол PASS хэвээр үлдэнэ: localhost дээр сүлжээгүй, ажил нь хоосон JSON буцаах л тул p95 ≈ 1.3–1.5ms байдаг. Тиймээс ийм босго юу ч шалгахгүй. Ийм учраас бид 20ms-ийг сонгосон.

## 6. Дүгнэлт

Сценарио → SLO → threshold шилжилтэд хамгийн хэцүү нь **босгын тоог сонгох** байсан. Зааврын жишээ тоо (`p95<200ms`) localhost дээр 1–5ms-ийн хариутай endpoint-д юу ч хэмжихгүй. Тиймээс эхлээд хэмжиж (p95 = 1.31ms, p99 = 5.4ms), дараа нь регрессийг барих хэмжээний (20ms) босго тогтоосон. Хоёр дахь хэцүү зүйл нь сценариогийн хэлийг k6-ийн метрик рүү буулгах байлаа. "Availability" гэдгийг k6 шууд хэмжихгүй тул `checks` rate-ийг SLI болгосон. Гэвч энэ нь **цагийн биш хүсэлтийн** хувь тул chaos туршилтаар хоёр өөр тоо гарсан. Chaos туршилт availability сценариогийн хэмжүүрийг **хэсэгчлэн баталсан**: сэргэх хугацааны шаардлага (≤ 15с) хангагдсан, учир нь сервер асмагц алдаа тэр секунддээ зогссон. Харин 90%-ийн availability SLO хүсэлтээр тооцоход 88.03% гарч зөрчигдсөн. Мөн нэг эвдрэл (crash) availability болон reliability хоёр SLO-г зэрэг унагаж байгааг харсан. Тиймээс SLI-уудыг давхардуулахгүй тодорхойлох нь чухал юм. PASS ба зориуд FAIL ажиллуулалт exit code 0 / 99-ийг өгсөн нь threshold-ыг CI-д quality gate болгоход шууд ашиглагдана. Эцэст нь сценарио дээр бичсэн тоо, SLO хүснэгт, `slo-test.js` гурав нэг эх сурвалжтай (ижил тоо) байх ёстойг практикаар ойлгосон.

## Нэмэлт: AI өнцөг

Сценари, скрипт болон тайланг AI туслах (Claude) ашиглан бэлдсэн. AI зааврын жишээ босгыг (`p95<200ms`) шууд хуулаагүй, бодит хэмжилтэд (p95 = 1.31ms) тулгуурлан 20ms болгож чангатгасан. Энэ нь "итгэмжтэй" болон "нарийн" шинжийг хангасан. Гэхдээ AI-ийн эхний автомат chaos ажиллуулалт сервер асаагүй байхад эхэлсэн тул 50% алдаатай буруу үр дүн өгсөн. Үүнийг лог шалгаж илрүүлээд дахин ажиллуулсан. Мөн README-д файлд хадгалагдаагүй урьдчилсан хэмжилтийн тоо (p95 ≈ 4ms) орсон байсныг `results/`-ийн тоогоор сольсон. Эдгээр нь AI-ийн гаргасан үр дүнг бодит гаралттай тулгаж шалгах шаардлагатайг харуулж байна.
